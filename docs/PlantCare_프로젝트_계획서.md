# 1. 프로젝트 기획 (Planning)

## 1-1. 프로젝트 목적 및 배경

**배경**
식물을 여러 종류 키우면 식물마다 물주기와 관리 방법이 달라서 기억하기 어려운 것 같다. 처음 들인 식물은 어떻게 관리해야 할지 모르겠고, 언제 물을 줬는지, 잎이 노래졌던 적이 있었는지도 금방 잊게 된다. 검색하면 일반적인 관리법은 나오지만 내 식물이 어떤 이력을 거쳤는지는 반영되지 않는다. 그래서 공공데이터로 만든 식물 도감에 내 식물의 관리 기록을 합쳐서, 도감 정보와 내 기록을 함께 보고 물어볼 수 있는 서비스를 만들려고 한다.

**서비스 설명**
사용자는 식물 도감에서 식물을 찾아 "내 식물로 추가"하고, 별명, 구매일, 위치, 대표 사진, 물주기 주기, 마지막으로 물 준 날짜를 입력한다. 내 식물 상세 화면에서는 도감의 기본 정보(계절별 물주기, 겨울 최저 온도 등)와 내 정보를 함께 본다. 홈 화면의 "오늘 할 일"에서 물주기를 D-day로 확인하고 "했어요"를 누르면 기록이 남는다. 잎이 노래지는 등 이상이 생기면 메모와 사진을 남긴다. RAG 챗봇에 "잎이 노래졌던 식물 있어?", "몬스테라 겨울에 물 어떻게 줘?"라고 물으면, 챗봇이 도감 정보와 내 기록에서 찾아 답하고 각각의 근거를 구분해서 보여준다.

**프로젝트 목표**
- 공공데이터로 식물 도감을 만들고, 도감에서 내 식물을 추가·수정·삭제할 수 있다.
- 내 식물 상세 화면에서 도감 정보와 내 정보를 함께 보여준다.
- 오늘 물 줄 식물을 D-day로 보여주고, "했어요" 한 번으로 케어 기록을 남긴다.
- RAG 챗봇이 도감 정보와 내 기록을 함께 참고해 답하고, 근거를 구분해서 보여준다.
- RAG 기반 질의응답을 직접 설계·구현하고, 구조와 한계까지 포트폴리오로 설명할 수 있게 한다.

## 1-2. 해결할 문제

식물을 처음 키우는 사용자는 물주기 방법과 관리 정보를 일일이 검색해야 한다. 식물을 2개 이상 키우는 사용자는 식물마다 다른 관리 항목과 내 식물의 관리 이력을 기억하기 어렵고, 식물에 이상이 생겼을 때 과거 기록을 찾는 데 시간이 걸린다. 또한 일반 검색 결과는 내 식물의 상황(위치, 구매일, 마지막 관리 날짜)과 맞지 않을 수 있다.

**PlantCare의 해결 방식**
- 공공데이터로 식물 도감을 만들어, 식물을 고르면 계절별 물주기 등 기본 정보를 바로 볼 수 있게 한다.
- 내 식물과 케어 기록을 한곳에 모아 MariaDB에 저장한다.
- 홈 화면의 "오늘 할 일"에서 물 줄 식물을 D-day로 보여준다.
- RAG 챗봇이 도감 정보와 내 기록을 함께 검색해 답하고, 근거를 구분해서 보여준다.
  - 내 기록: 구매일, 케어 기록, 메모, 위치, 내가 정한 물주기 주기
  - 도감 정보: 식물 종류별 계절 물주기 등 일반 기준
  - 예: "몬스테라 겨울에 물 어떻게 줘?" → 도감의 겨울 물주기 기준과 내 기록의 마지막 물 준 날을 합쳐 답한다.
- 근거가 없는 내용은 추측하지 않고 "확인된 정보가 없습니다"라고 답한다.

## 1-3. 타깃 사용자

| 사용자 | 원하는 것 |
| --- | --- |
| 식물을 2개 이상 키우는 초보~중급 사용자 | 식물마다 다른 물주기·관리 정보를 한곳에서 확인하고 싶다 |
| 식물을 새로 들인 사용자 | 이 식물을 어떻게 관리해야 하는지 바로 알고 싶다 |

**대표 시나리오**
1. 식물을 산 날 도감에서 "몬스테라"를 찾아 기본 정보(계절별 물주기 등)를 확인한다.
2. "내 식물로 추가"를 누르고 별명(몬이), 구매일, 위치, 대표 사진, 물주기 주기, 마지막으로 물 준 날짜를 입력한다.
3. 내 식물 상세 화면에서 도감 정보와 내 정보를 함께 본다.
4. 홈 화면 "오늘 할 일"에서 물주기를 확인하고 "했어요"를 누르면 기록된다.
5. 잎이 노래지면 메모와 사진을 남긴다.
6. RAG 챗봇에 "잎이 노래졌던 식물 있어?", "몬스테라 겨울에 물 어떻게 줘?"라고 물으면, 도감 정보와 내 기록에서 찾아 답하고 근거를 구분해서 보여준다.

## 1-4. 서비스 주요 기능

- **식물 도감**: 공공데이터를 정리해 둔 식물 목록(사진 포함)과 이름 검색, 광도 조건 필터. 사용자는 읽기만 가능
- **내 식물 관리**: 도감에서 고른 식물을 내 식물로 추가, 수정·삭제 (별명, 구매일, 위치, 물주기 주기, 마지막으로 물 준 날짜, 대표 사진(선택)). 도감에 없는 식물은 종류를 직접 입력해 도감 정보 없이 등록할 수 있다.
- **내 식물 상세**: 도감의 기본 정보(계절별 물주기, 광요구도, 배치장소, 겨울 최저 온도 등)와 내 정보를 함께 표시
- **오늘 할 일**: 내가 정한 물주기 주기로 물 줄 식물을 D-day로 표시하고, "했어요"를 누르면 케어 기록으로 저장. 도감의 계절별 물주기 안내를 참고로 함께 보여준다.
- **케어 기록·다이어리**: 물주기·비료·분갈이 기록과 이상 기록(메모·사진)을 날짜순으로 표시
- **검색·필터**: 식물 이름, 위치, 케어 종류로 조회
- **RAG 식물 도우미 (핵심)**: 도감 정보와 내 기록을 합쳐 답하고, 두 근거를 구분해서 표시

**제외 범위 (1차)**
- 공공데이터에 없는 정보: 시작 가이드, 물주기 일수·비료 주기 같은 숫자 값
- 물주기와 비료는 도감의 문구(흙 상태 기준 물주기, 비료 요구 정도)로만 보여주고, D-day는 내가 정한 물주기 주기로만 계산한다.
- 커뮤니티·나눔·거래, 푸시 알림, 사진 기반 식물 식별·병충해 진단, 센서 연동, 로그인·다중 사용자

## 1-5. 데이터 수집 및 활용

데이터 원본은 MariaDB에 저장하고, AI 검색용 벡터 데이터는 Chroma에 따로 둔다.

| 데이터 | 수집 방법 | 사용 목적·관리 |
| --- | --- | --- |
| 식물 도감 (`plant_species` 테이블) | 공공데이터(농촌진흥청 실내정원용 식물)를 농사로 OpenAPI의 목록(gardenList)과 상세(gardenDtl)로 받아 DB에 저장. 도감 사진은 목록 응답의 사진 주소를 저장 | 도감 목록·검색·필터, 상세 정보, 챗봇 근거. 출처와 이용 조건을 기록 |
| 내 식물 (`plants` 테이블) | 사용자가 도감에서 추가하고 별명·구매일·위치·물주기 주기·마지막으로 물 준 날짜(첫 물주기 기록으로 저장)·사진 입력. 개발·검증용은 팀이 샘플 데이터를 작성 | 내 식물 목록, D-day 계산, 챗봇 검색 대상 |
| 케어 기록 (`care_logs` 테이블) | "했어요" 버튼과 메모·사진 입력. 식물 ID로 내 식물과 연결 | 마지막 관리일 계산, 이상 기록 검색, 챗봇 근거 |
| 식물 사진 (대표 사진, 케어 기록 사진) | 사용자가 업로드 | 식물 목록·다이어리 표시용. 파일은 폴더에 저장하고 DB에는 경로만 기록 |
| 벡터 데이터 (Chroma) | MariaDB의 도감 정보와 내 기록에서 각각 생성 | 검색 전용. 도감과 내 기록을 구분해 저장하고, 원본이 바뀌면 다시 만들거나 갱신 |

**도감에 저장하는 항목**
식물명, 학명, 영명, 유통명, 원산지, 성장 높이·넓이, 잎 형태, 번식 시기, 비료 정보, 토양 정보, 계절별 물주기, 겨울 최저 온도, 광요구도, 배치장소, 관리수준, 관리요구도, 생육 온도, 습도, 기능성 정보(식물 설명), 사진 주소(썸네일·원본)

**도감 데이터 처리 방식**
- 코드로 오는 값(계절별 물주기, 겨울 최저 온도, 광요구도, 배치장소, 관리수준, 관리요구도, 생육 온도, 습도)은 API가 코드와 함께 주는 코드명(`...CodeNm`)을 그대로 저장해 표시한다.
- 광요구도와 배치장소처럼 값이 여러 개인 항목은 쉼표로 구분되어 오므로 나누어 저장한다.
- 값이 비어 있는 항목은 "도감에 정보가 없습니다"로 표시한다.

**개인정보·권리 유의사항**
- 공공데이터포털은 이용허락범위를 "제한 없음"으로, 농사로는 공공누리 유형3(출처 표시, 변경 금지)으로 표기하고 있어 더 엄격한 유형3 기준으로 사용한다. 화면에 출처를 표시하고 원문 내용은 고쳐 쓰지 않는다.
- 참고 출처: 농촌진흥청 실내정원용 식물 — 공공데이터포털 https://www.data.go.kr/data/15059042/openapi.do, 농사로 OpenAPI https://api.nongsaro.go.kr/sample/rest/garden/garden.jsp
- API 키(공공데이터 인증키, AI API 키)와 DB 접속 정보(.env), 벡터 DB는 `.gitignore`로 제외한다.

## 1-6. AI 활용 여부

RAG 챗봇이 서비스의 중심 기능이다.

**적용 방식**
1. MariaDB의 도감 정보와 내 식물·케어 기록을 각각 문서로 변환해 Chroma에 저장한다 (문서 종류를 구분해 표시).
2. 질문에 식물 이름이 있으면 그 식물의 내 기록과 도감 정보를 DB에서 가져오고, 없으면 Chroma에서 관련 기록을 검색한다 (top-k).
3. 날짜 계산(마지막 물 준 날 + 내가 정한 주기)은 코드에서 처리한다.
4. 가져온 결과와 계산 결과를 하나의 context 문자열로 묶어 프롬프트에 넣는다.
5. Gemini가 그 context를 근거로 답하고, 내 기록과 도감 정보를 구분해서 보여준다.

**답변 원칙**
- 내 기록과 도감 정보를 **항상 구분해서** 표시한다.
- 도감 정보는 식물 종류 단위의 일반 기준이라 내 환경과 다를 수 있다고 안내한다.
- 도감에 없는 식물은 "도감 정보가 없습니다"라고 구분해서 답하고, 내 기록만으로 안내한다.
- 근거가 없는 내용은 추측하지 않고 "확인된 정보가 없습니다"라고 답한다.

**날짜 질문 처리 계획**
"가장 최근에 물 준 날", "다음에 물 줄 날"처럼 날짜가 중요한 질문은 임베딩 검색만으로는 부정확할 수 있다. 해당 식물의 기록을 DB에서 날짜순으로 조회하고 날짜 계산은 코드에서 처리해, 정리된 결과를 LLM에 넘기는 방식으로 구현할 계획이다.

**챗봇 없이도 동작하는 기능**
도감 검색, 내 식물 관리, 오늘 할 일 D-day, 케어 기록은 챗봇 API와 무관하게 동작한다. API 호출이 실패해도 핵심 기능은 사용할 수 있다.

# 2. MVP 계획 (MVP Planning)

개발 기간은 11.19 ~ 11.25이다. 11.19에는 기획·설계 문서 작성과 농사로 API 키 신청을 진행하고, 11.20부터 아래 3단계로 개발한다. 서비스의 중심 기능이 RAG 챗봇이므로 사진, 다이어리, 필터 같은 부가 기능보다 챗봇을 먼저 구현한다.

## 2-1. MVP 1단계: 기본 흐름 (11.20 ~ 11.21)

AI 없이 앱이 동작하는 상태를 만든다.

- DB 테이블 4개(`plant_species`, `species_tags`, `plants`, `care_logs`)를 생성한다. `care_logs`는 기록 종류(물주기, 비료, 분갈이, 이상)를 구분해 저장한다.
- 도감 데이터: API 키 발급 전에는 농사로 샘플 화면에서 확인한 식물 10종을 `plant_species`에 직접 입력해 개발하고, 키 발급 후 농사로 OpenAPI로 가져온 데이터로 교체한다.
- 도감 목록, 이름 검색, 광요구도 필터, 상세 화면(도감 사진 포함)을 구현한다.
- 도감에서 "내 식물로 추가"(별명, 구매일, 위치, 물주기 주기, 마지막으로 물 준 날짜, 대표 사진(선택))를 구현하고, 도감에 없는 식물은 종류를 직접 입력해 등록한다. 사진이 있는 등록은 FormData로 전송하고, 사진 저장과 형식·크기 검증도 구현한다.
- 내 식물 수정·삭제와 내 식물 상세(도감 정보와 내 정보를 함께 표시)를 구현한다.
- 오늘 할 일: 마지막으로 물 준 날짜와 내가 정한 물주기 주기로 D-day를 계산해 표시하고, "했어요"를 누르면 케어 기록으로 저장한다.
- 비료·분갈이 기록과 이상 기록(메모)을 저장한다.

완료 기준: 도감에서 식물을 골라 대표 사진과 함께 등록하고, 홈에서 D-day를 확인하고, "했어요"와 메모가 기록된다.

## 2-2. MVP 2단계: RAG 챗봇 (11.22 ~ 11.23)

- 도감 정보와 내 기록을 각각 문서로 만들어 Chroma에 저장한다.
- 식물 이름이 있는 질문은 DB에서 해당 식물의 내 기록과 도감 정보를 조회하고, 이름이 없는 질문은 Chroma에서 검색한다.
- 날짜 질문("가장 최근에 물 준 날", "다음에 물 줄 날")은 DB 조회와 코드 계산 결과를 Gemini에 전달한다.
- 답변에 "내 기록"과 "도감" 근거를 구분해 표시하고, 근거가 없으면 "확인된 정보가 없습니다"로 답한다.
- 도감, 내 식물, 케어 기록이 바뀌면 Chroma 검색 데이터를 갱신하고, 갱신 실패를 확인할 수 있게 한다.

완료 기준: "잎이 노래졌던 식물 있어?"와 도감에 있는 식물의 겨울 물주기 질문에 근거를 구분해 답한다.

## 2-3. MVP 3단계: 부가 기능과 마무리 (11.24 ~ 11.25)

- 이상 기록에 사진 첨부를 구현한다.
- 케어 기록 다이어리(날짜순)와 내 식물 검색·필터(이름, 위치, 케어 종류)를 구현한다.
- 샘플 데이터(식물, 케어 기록, 이상 기록)를 입력하고 챗봇 질문 시나리오를 점검한다.
- 도감 출처 표시와 로딩·빈 결과·실패 안내를 적용한다.

## 2-4. 일정 관리

**일정이 밀릴 때 제외하는 순서**
1. 내 식물 검색·필터
2. 케어 기록 다이어리 화면
3. 이상 기록 사진 첨부

MVP 1단계와 2단계는 제외하지 않는다.

**위험 요소와 대응**
- API 키 승인이 늦어지면 샘플 입력 데이터로 MVP 1단계를 진행하고, 키 발급 후 데이터를 교체한다.
- 챗봇 예시 식물(몬스테라)이 도감 데이터에 없으면 도감에 있는 식물로 예시를 바꾼다.

## 4-3. 서비스 정책

- 도감은 공공데이터를 정리한 읽기 전용 목록이며, 사용자는 수정할 수 없다. 값이 비어 있으면 "도감에 정보가 없습니다"로 표시한다.
- 내 식물의 별명, 물주기 주기, 마지막으로 물 준 날짜는 필수이고, 구매일·위치·대표 사진은 선택한다. 마지막으로 물 준 날짜의 기본값은 오늘이다.
- 도감에 없는 식물은 종류를 직접 입력해 등록할 수 있으며, 이 경우 도감 정보가 없다고 구분해서 표시한다.
- D-day는 내가 정한 물주기 주기로만 계산한다. 도감의 물주기와 비료 정보는 문구(흙 상태 기준, 요구 정도)로만 참고용으로 보여주고, 시작 가이드와 일수·주기 같은 숫자 값은 제공하지 않는다.
- 케어 기록 종류는 물주기, 비료, 분갈이, 이상 기록(메모·사진)이다.
- 삭제 전에 확인을 받는다. 내 식물을 삭제하면 연결된 케어 기록과 사진 파일도 함께 정리하고 검색 데이터(Chroma)도 갱신한다.
- 사진은 허용 형식과 크기를 정해 서버에서도 검증한다. 파일은 폴더에 저장하고 DB에는 경로만 기록한다.
- 검색은 식물 이름, 위치, 케어 종류를 대상으로 하며 결과가 없으면 안내한다.
- 챗봇은 도감 정보와 내 기록만 근거로 사용한다. 질문과 참고 정보가 외부 AI로 전송될 수 있음을 알린다.
- 챗봇 답변은 식물 상태 진단이나 치료 방법이 아니며, 이상이 심하면 전문가 확인이 필요하다고 안내한다.
- 로그인과 개인정보 수집은 1차 범위에서 제외한다.

# 5. 시스템 설계 (Architecture)

## 5-1. 시스템 아키텍처

```
사용자 브라우저
   │
   ▼
Next.js 화면 / 컴포넌트
   │ fetch
   ▼
FastAPI API ──► MariaDB: 도감, 내 식물, 케어 기록
   │        └─► 업로드 폴더: 대표 사진, 이상 기록 사진
   │
   └─ 챗봇 질문 ─► (식물 이름 있음) MariaDB 조회
                   (식물 이름 없음) Chroma 검색: 도감 문서, 내 기록 문서
                        │ 검색 결과 + 코드로 계산한 날짜
                        ▼
                   Google Gemini API
                        │
                        ▼
              FastAPI → Next.js → 사용자

[도감 가져오기]
농사로 OpenAPI (gardenList, gardenDtl) ──► 가져오기 스크립트 ──► MariaDB plant_species
```

- **도감 가져오기 스크립트**: 개발자가 실행하는 별도 명령이다. 목록으로 식물 번호를 받고, 번호마다 상세를 호출해 `plant_species`에 저장한다. 같은 번호는 덮어쓴다(업서트).
- **D-day 계산**: FastAPI가 코드로 한다. 가장 최근 물주기 기록 날짜에 물주기 주기를 더하고 오늘 날짜를 뺀다.
- **챗봇**: 날짜 질문은 DB 조회와 코드 계산 결과를 Gemini에 전달한다. 답변에는 "내 기록"과 "도감" 근거를 구분해서 표시한다.
- **키 관리**: 농사로 인증키, Gemini 키, DB 접속 정보는 백엔드 `.env`에 두고 `.gitignore`로 제외한다. 브라우저에는 전달하지 않는다.
- **전송 형식**: 사진이 있는 등록은 FormData, 수정과 채팅은 JSON을 사용한다.

## 5-2. 데이터베이스 ERD 및 데이터 구조

로그인과 다중 사용자는 1차 범위가 아니므로 사용자 테이블은 두지 않는다.

```
plant_species (식물 도감)
   ├── 1 : N ── species_tags (광요구도·배치장소)
   └── 1 : N ── plants (내 식물)   ※ 도감 식물을 고른 경우만 연결 (species_id는 NULL 허용)
                   └── 1 : N ── care_logs (케어 기록)
```

**plant_species (식물 도감, 읽기 전용)**

| 컬럼 | 타입 | 설명 (농사로 항목) |
| --- | --- | --- |
| id | BIGINT PK | 고유 번호 |
| cntnts_no | VARCHAR UNIQUE | 농사로 콘텐츠 번호 (`cntntsNo`), 다시 가져올 때 기준 |
| name | VARCHAR | 식물명 (`cntntsSj`) |
| scientific_name, english_name, distribution_name | VARCHAR | 학명, 영명, 유통명 |
| family_name, origin | VARCHAR | 과명, 원산지 |
| growth_height, growth_width | VARCHAR | 성장 높이·넓이 |
| leaf_form | VARCHAR | 잎 형태 |
| propagation_period | VARCHAR | 번식 시기 |
| fertilizer_info, soil_info | VARCHAR | 비료 정보, 토양 정보 (문구) |
| water_spring, water_summer, water_autumn, water_winter | VARCHAR | 계절별 물주기 (`watercycle*CodeNm`) |
| winter_min_temp | VARCHAR | 겨울 최저 온도 (`winterLwetTpCodeNm`) |
| manage_level, manage_demand | VARCHAR | 관리수준, 관리요구도 |
| growth_temp, humidity | VARCHAR | 생육 온도, 습도 |
| function_info | TEXT | 기능성 정보 (식물 설명) |
| thumb_url, image_url | VARCHAR | 목록 응답의 첫 번째 사진 주소 |
| source, fetched_at | VARCHAR, DATETIME | 출처("농사로"), 가져온 시각 |

비어 있는 값은 NULL로 저장하고, 화면에서 "도감에 정보가 없습니다"로 표시한다.

**species_tags (광요구도·배치장소)**: 값이 여러 개인 항목을 한 행에 하나씩 나누어 저장한다.

| 컬럼 | 타입 | 설명 |
| --- | --- | --- |
| id | BIGINT PK | 고유 번호 |
| species_id | BIGINT FK | `plant_species.id`, 도감 식물이 지워지면 함께 삭제 |
| tag_type | ENUM('light', 'placement') | 광요구도 / 배치장소 |
| value | VARCHAR | 코드명 (예: 중간 광도(800~1,500 Lux)) |

광도 필터는 `tag_type = 'light'`와 `value`로 조회한다.

**plants (내 식물)**

| 컬럼 | 타입 | 설명 |
| --- | --- | --- |
| id | BIGINT PK | 고유 번호 |
| species_id | BIGINT FK NULL | `plant_species.id`, 도감에서 고른 경우만 |
| custom_species_name | VARCHAR NULL | 도감에 없는 식물의 종류 직접 입력 |
| nickname | VARCHAR NOT NULL | 별명 |
| location | VARCHAR NULL | 위치 |
| purchase_date | DATE NULL | 구매일 |
| water_interval_days | INT NOT NULL | 물주기 주기(일), 1 이상 |
| photo_path | VARCHAR NULL | 대표 사진 경로 |
| created_at, updated_at | DATETIME | 생성·수정 시각 |

`species_id`와 `custom_species_name` 중 하나는 반드시 있어야 한다. 도감 정보 없이 등록한 식물은 화면에 도감 정보가 없다고 구분해서 표시한다.

**care_logs (케어 기록)**

| 컬럼 | 타입 | 설명 |
| --- | --- | --- |
| id | BIGINT PK | 고유 번호 |
| plant_id | BIGINT FK | `plants.id`, 식물을 삭제하면 기록도 함께 삭제 |
| log_type | ENUM('water', 'fertilizer', 'repot', 'issue') | 물주기, 비료, 분갈이, 이상 기록 |
| logged_at | DATE | 기록 날짜 |
| memo | TEXT NULL | 메모 (이상 기록은 메모 또는 사진 필수) |
| photo_path | VARCHAR NULL | 이상 기록 사진 경로 |
| created_at | DATETIME | 저장 시각 |

**마지막으로 물 준 날짜 처리**: `plants`에 따로 두지 않는다. 식물을 등록할 때 사용자가 입력한 "마지막으로 물 준 날짜"(기본값 오늘)를 첫 번째 물주기 기록(`log_type = 'water'`)으로 저장한다. D-day는 가장 최근 물주기 기록 날짜를 기준으로 계산하므로 날짜가 한 곳에만 있어 어긋나지 않는다.

**인덱스**: `plant_species(name)`, `species_tags(tag_type, value)`, `care_logs(plant_id, log_type, logged_at)`

**Chroma 검색 데이터 (두 컬렉션으로 구분)**

| 컬렉션 | 문서 내용 | 메타데이터 |
| --- | --- | --- |
| species_docs | 도감 한 식물의 이름, 계절별 물주기, 광요구도, 배치장소, 비료·토양 정보, 설명을 한 문서로 구성 | species_id, name |
| care_docs | 내 식물 한 건의 기록(종류, 날짜, 메모)과 별명, 위치 | plant_id, log_id, log_type, logged_at |

도감과 내 기록을 분리해서 저장해야 답변의 근거를 구분해 표시할 수 있다. 도감 가져오기, 내 식물 수정·삭제, 기록 추가가 끝나면 해당 문서를 갱신하고, 갱신이 실패하면 오류를 기록한다.

**삭제 처리**: 내 식물을 삭제하면 연결된 케어 기록은 DB가 함께 삭제하고, 사진 파일과 Chroma 문서는 백엔드가 정리한다. 도감 데이터는 사용자가 삭제할 수 없다.

**백업 대상**: MariaDB 데이터, 업로드 폴더, Chroma 폴더를 각각 구분한다. Chroma는 DB에서 다시 만들 수 있다.

## 5-3. API 명세서

백엔드(`main.py`)의 API이고, 모든 경로는 `main.py` 한 파일에 둔다. 기본 주소는 `http://127.0.0.1:8000`이며, 프런트엔드는 `service/api.js`에서 호출한다. 사진이 있는 요청은 FormData, 나머지는 JSON을 사용한다. FormData의 Content-Type은 브라우저가 경계값과 함께 설정하도록 직접 지정하지 않는다.

| --- | --- | --- |

| GET `/species/{id}` | 도감 번호 | 도감 항목 전체(5-2의 `plant_species` 컬럼)와 `tags`(`light`, `placement` 배열). 값이 없는 항목은 `null`. 없는 번호는 404 |

### 내 식물

| 메서드·경로 | 요청 | 응답·처리 |
| --- | --- | --- |
| GET `/plants` | 쿼리(MVP 3단계): `keyword`(이름), `location`, `log_type` | 식물 배열: `id`, `nickname`, `species_name`, `location`, `photo_url` |
| POST `/plants` | FormData: `species_id` 또는 `custom_species_name`, `nickname`, `water_interval_days`, `last_watered_at`, 선택 `purchase_date`, `location`, `photo` | 저장 후 `{"id": n}`(201). 마지막으로 물 준 날짜로 첫 물주기 기록도 함께 저장 |
| GET `/plants/{id}` | 식물 번호 | 내 정보, `species`(도감 정보, 직접 입력한 식물은 `null`), 최근 기록, `next_water_date`, `d_day`. 없는 번호는 404 |
| PUT `/plants/{id}` | FormData: 수정할 필드, 선택 `photo`(새 사진), `remove_photo` | 수정 결과. 없는 번호는 404 |
| DELETE `/plants/{id}` | 식물 번호 | 식물, 케어 기록, 사진 파일을 삭제하고 Chroma 문서를 정리. 없는 번호는 404 |

대표 사진은 `photo_url`로 내려가고, 없으면 도감 `thumb_url`, 둘 다 없으면 프런트엔드가 기본 이미지를 표시한다.

### 케어 기록과 오늘 할 일

| 메서드·경로 | 요청 | 응답·처리 |
| --- | --- | --- |
| POST `/plants/{id}/water` | JSON: 선택 `logged_at`(기본 오늘) | 물주기 기록 저장 후 갱신된 `next_water_date`, `d_day` |
| POST `/plants/{id}/logs` | FormData: `log_type`(`fertilizer`, `repot`, `issue`), 선택 `logged_at`(기본 오늘), `memo`, 선택 `photo` | 저장 후 기록 한 건. 이상 기록은 메모 또는 사진이 반드시 있어야 한다 |
| GET `/plants/{id}/logs` | 쿼리: 선택 `log_type` | 날짜 내림차순 기록 배열: `id`, `log_type`, `logged_at`, `memo`, `photo_url` |
| GET `/today` | 없음 | 식물 배열을 `d_day` 오름차순으로 반환: `plant_id`, `nickname`, `location`, `photo_url`, `last_watered_at`, `water_interval_days`, `next_water_date`, `d_day`, `season_water_text`(현재 계절의 도감 물주기 문구) |

**이상 기록에 보내는 항목 (`/plants/{id}/logs`)**

| MVP 단계 | 보내는 항목 |
| --- | --- |
| MVP 1단계 | 기록 종류(`log_type`), 날짜(`logged_at`), 메모(`memo`) |
| MVP 3단계 | 위 항목 + 사진(`photo`) |

경로는 같고 MVP 3단계에서 `photo` 항목만 추가로 받는다.

**D-day 계산**: `next_water_date = 가장 최근 물주기 기록 날짜 + water_interval_days`, `d_day = next_water_date − 오늘`이다. `d_day`가 0 이하이면 화면에 "오늘 물 주기" 또는 "N일 지남"으로 표시한다. 현재 계절은 3~5월 봄, 6~8월 여름, 9~11월 가을, 12~2월 겨울로 구분한다.

### 식물 도우미

| 메서드·경로 | 요청 | 응답·처리 |
| --- | --- | --- |
| POST `/chat` | JSON: `{"question": "잎이 노래졌던 식물 있어?"}` | `{"answer": "...", "sources": [{"type": "my_record" 또는 "species", "title", "text"}]}`. 근거가 없으면 `answer`에 "확인된 정보가 없습니다"를 담고 `sources`는 빈 배열 |
| POST `/rag/rebuild` | 없음 | `{"species_docs": n, "care_docs": n, "failed": [...]}`. 도감 적재, 식물·기록 변경 후 자동 호출하고, 실패하면 `failed`에 담아 확인할 수 있게 한다 |

**챗봇 처리 순서**: 질문에 식물 이름이 있으면 DB에서 해당 식물의 내 기록과 도감 정보를 조회하고, 없으면 Chroma(`species_docs`, `care_docs`)에서 검색한다. 날짜 계산은 코드로 하고 결과를 Gemini에 전달한다. `sources`의 `type`으로 화면이 "내 기록"과 "도감" 근거를 구분해서 표시한다.

### 입력 규칙과 오류 응답

| 항목 | 규칙 |
| --- | --- |
| `nickname` | 필수, 1~50자 |
| `water_interval_days` | 필수, 1 이상의 정수 |
| `last_watered_at` | 필수, 오늘 이전 날짜. 화면의 기본값은 오늘 |
| `species_id`, `custom_species_name` | 둘 중 하나는 필수 |
| `photo` | 허용 형식 jpg, png, webp, 최대 5MB. 서버에서도 검증 |
| `log_type` | `fertilizer`, `repot`, `issue` 중 하나 |

| 상태 코드 | 의미 |
| --- | --- |
| 200, 201 | 성공, 생성 성공 |
| 404 | 없는 도감·식물 번호 |
| 413, 415 | 사진 크기 초과, 허용하지 않는 형식 |
| 422 | 입력 규칙 위반 (Pydantic 검증 실패) |
| 503 | AI 호출 또는 Chroma 갱신 실패 (`/chat`, `/rag/rebuild`에서만 발생하고 다른 API는 영향을 받지 않는다) |

모든 오류는 `{"detail": "안내 문구"}` 형태로 응답한다.

## 5-4. 화면 설계서

화면도 MVP 단계 순서대로 개발한다. 로그인, 관리자, 도감 수정 화면은 1차 범위에 포함하지 않는다.

### MVP 1단계: 도감과 기본 흐름

| 화면·기능 | 경로 | 화면에 표시할 내용과 사용자 동작 | 요구사항 |
| --- | --- | --- | --- |
| 홈·오늘 할 일 | `/` | 물 줄 식물을 D-day 순으로 표시한다(사진, 별명, 위치, D-day). D-day가 0 이하이면 "오늘 물 주기" 또는 "N일 지남"으로 표시한다. "했어요" 버튼을 누르면 물주기가 기록되고 D-day가 갱신된다. 도감의 계절별 물주기 문구를 참고로 함께 표시한다. 내 식물이 없으면 도감으로 이동하는 안내를 표시한다 | FR-09, FR-07 |
| 도감 목록·검색 | `/species` | 식물 사진(썸네일)과 이름을 카드로 표시한다. 이름 검색창과 광요구도 필터(낮은·중간·높은 광도)를 사용한다. 결과가 없으면 안내하고, 카드를 누르면 상세로 이동한다 | FR-01 |
| 도감 상세 | `/species/[id]` | 사진, 식물명·학명·영명·유통명, 계절별 물주기, 광요구도, 배치장소, 겨울 최저 온도, 비료·토양 정보, 설명, 출처를 표시한다. 값이 없으면 "도감에 정보가 없습니다"로 표시한다. "내 식물로 추가" 버튼으로 추가 화면으로 이동한다 | FR-02 |
| 내 식물 추가 | `/plants/new` | 도감에서 고른 식물(또는 종류 직접 입력)에 별명, 물주기 주기, 마지막으로 물 준 날짜(기본값 오늘), 구매일, 위치, 대표 사진(선택)을 입력한다. 도감의 계절별 물주기 문구를 입력칸 옆에 참고로 표시한다. 사진은 허용 형식과 크기를 안내하고, 업로드 실패를 안내한다. 저장하면 첫 물주기 기록이 함께 만들어진다 | FR-04 |
| 내 식물 목록 | `/plants` | 식물 카드(사진, 별명, 종류, 위치)를 표시하고 상세로 이동한다. 사진은 대표 사진, 없으면 도감 사진, 둘 다 없으면 기본 이미지 순서로 표시한다 | FR-05, FR-06 |
| 내 식물 상세 | `/plants/[id]` | 도감 정보와 내 정보(별명, 구매일, 위치, 주기, 마지막 물 준 날짜)를 구분해서 표시한다. 도감 정보 없이 등록한 식물은 그렇다고 표시한다. 물주기·비료·분갈이 기록 버튼과 이상 기록(메모) 입력, 최근 기록 목록, 수정·삭제 버튼을 둔다. 삭제 전에 확인을 받는다 | FR-06, FR-07, FR-05 |
| 내 식물 수정 | `/plants/[id]/edit` | 기존 값을 불러와 수정하고 저장한다. 대표 사진을 바꾸거나 지울 수 있다 | FR-05 |

### MVP 2단계: 식물 도우미

| 화면·기능 | 경로 | 새로 추가할 내용과 사용자 동작 | 요구사항 |
| --- | --- | --- | --- |
| 식물 도우미 | 공통 사이드바 | 질문 입력·전송, 응답 대기 표시, 답변과 근거(내 기록, 도감)를 구분해서 표시한다. 근거가 없으면 "확인된 정보가 없습니다"로 표시한다. 도감 정보가 없는 식물은 그렇다고 구분하고, 도감은 일반 기준이라는 안내와 전문가 확인 안내를 표시한다 | FR-12, FR-13 |
| 챗봇 오류 안내 | 공통 사이드바 | AI 요청이 실패하거나 검색 데이터 갱신이 실패하면 사이드바에 안내한다. 도감, 내 식물, 오늘 할 일, 케어 기록은 그대로 동작한다 | FR-14, FR-15 |

### MVP 3단계: 부가 기능과 안정화

| 화면·기능 | 경로 | 새로 추가하거나 개선할 내용 | 요구사항 |
| --- | --- | --- | --- |
| 이상 기록 사진 | `/plants/[id]` | 이상 기록 입력에 사진 선택을 추가한다. 허용 형식과 크기를 안내하고 업로드 실패를 안내한다 | FR-11 |
| 케어 기록·다이어리 | `/plants/[id]/diary` | 식물별 물주기·비료·분갈이·이상 기록을 날짜순으로 표시하고, 기록 종류와 이상 기록 사진을 함께 보여준다 | FR-08 |
| 내 식물 검색·필터 | `/plants` | 식물 이름, 위치, 케어 종류로 조회한다. 결과가 없으면 안내한다 | FR-10 |
| 상태·오류 안내 | 전체 화면 | 로딩, 빈 결과, 실패를 구분해서 안내한다. 저장 중 중복 제출을 막고, 모바일 폭과 키보드로 주요 버튼을 사용할 수 있는지 확인한다 | FR-14 |

## 6-2. 실행 방법

| 구분 | 명령 | 주소 |
| --- | --- | --- |
| 프런트엔드 | `npm run dev` | http://localhost:3000 |
| 백엔드 | `uvicorn main:app --reload` | http://127.0.0.1:8000 (API 확인은 `/docs`) |
| DB 생성 | MariaDB에서 `sql/schema.sql` 실행 | |
| 도감 적재 | `python scripts/import_species.py` | |

프런트엔드의 `NEXT_PUBLIC_API_SERVER`에 백엔드 주소를 설정한다. 이 변수에는 API 키를 넣지 않는다. 농사로 인증키, Gemini 키, DB 접속 정보는 백엔드 `.env`에만 둔다.

Git에 올리지 않는 것: `.env`, `.env.local`, `backend/uploads/`, `backend/chroma_db/`, `node_modules/`, `__pycache__/`
